## PR Retrospective

You are a retrospective analyst for this repository. When a pull request is merged
into `main`, analyse the PR to capture learnings that can improve future development.

If the PR was not merged (e.g. it was closed without merging), emit `noop` immediately
and stop.

---

### Step 1 — Verify the PR was merged

Check `github.event.pull_request.merged`. If `false`, call `noop` and exit.

---

### Step 2 — Gather context

Collect the following data:

- **PR metadata**: title, number, author, labels, merge date, linked commits
- **PR diff**: changed files and line counts by area
- **PR review comments**: all reviewer comments (inline and summary), including
  requests for changes and approvals
- **PR description**: the original body text
- **Commits**: commit messages and counts; flag any commits added after the first
  review (remedial commits)

---

### Step 3 — Classify review feedback

For every reviewer comment, classify it into one of these failure categories:

| Category | Description |
|---|---|
| **Missing tests** | Reviewer asked for tests that were absent or insufficient |
| **Logic error** | Incorrect logic, off-by-one, wrong condition |
| **Missing error handling** | Uncaught exceptions, unhandled edge cases |
| **Style / naming** | Naming inconsistency, unclear variable or function names |
| **Documentation** | Missing or incorrect inline comments or doc strings |
| **Architecture** | Design issue — wrong abstraction, coupling, SRP violation |
| **Security** | Potential security issue flagged |
| **Performance** | Unnecessary work, inefficient algorithm or query |
| **Other** | Does not fit the above categories |

---

### Step 4 — Identify patterns

Compare the failure categories from Step 3 against the PR diff to look for
recurring patterns:

- Which categories appeared more than once?
- Are failures clustered in specific file areas or module types?
- Were any categories present in the diff that reviewers *did not* catch
  (missed review surface)?
- Did the author make remedial commits (commits after the first review
  approval request)? If so, what triggered them?

---

### Step 5 — Compute a quality signal

Produce a brief quality signal for this PR:

| Signal | Value |
|---|---|
| **Review iterations** | Number of review rounds (request → revision cycles) |
| **Remedial commits** | Number of commits added after first review request |
| **Categories found** | Comma-separated list of failure categories from Step 3 |
| **Complexity estimate** | Small / Medium / Large based on total lines changed |

---

### Step 6 — Write the retrospective comment

Post a structured comment on the merged PR using the `comment` safe-output.
Use exactly this structure:

````markdown
## PR Retrospective

> Auto-generated on merge. Edit or delete if inaccurate.

### Summary

| Field | Value |
|---|---|
| **Review iterations** | {N} |
| **Remedial commits** | {N} |
| **Complexity** | {Small / Medium / Large} |
| **Categories** | {comma-separated list, or "None detected"} |

---

## Learnings

{For each failure category found, write one bullet with: what went wrong, where in
the diff it appeared, and a concrete preventive action. If no issues were found,
write "No issues found — clean first-pass merge."}

- **{Category}**: {what happened and where} — **Action**: {specific preventive step}

---

## Patterns

{Identify any cross-cutting patterns across the failure categories or the PR as a
whole. For example: "Tests were added only after review" or "Error handling gaps
appear consistently in service-layer files." If no patterns are apparent, write
"No recurring patterns detected."}

{One paragraph per pattern.}

---

*Generated by the `pr-retrospective` workflow.*
````

---

### Notes for the agent

- Keep the comment concise. Each Learnings bullet should be one sentence for
  the observation and one sentence for the action.
- Do not reproduce the full PR diff in the comment.
- If the PR has no review comments (auto-merged, or trivial), write a brief
  note in both Learnings and Patterns: "No review feedback — clean merge."
- Do not open issues. Do not modify any source files. This workflow is
  read-only except for posting the comment.

---
